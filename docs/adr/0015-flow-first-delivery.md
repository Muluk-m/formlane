# ADR-0015: Code-orchestrated delivery Flow

Status: accepted. Supersedes the hierarchical Crew orchestration in [ADR-0013](0013-python-postgres-services.md) and the manager-delegation part of [ADR-0012](0012-durable-agent-harness.md). DBOS recovery, leases, cancellation and the acceptance gate in [ADR-0014](0014-dbos-node-recovery.md) are unchanged.

## Context

The hierarchical Crew let Mike choose every next specialist. Fixed rules ("delegate Emma and Bob once", "Alex at most twice", "Alex validation before David review") lived in a long manager prompt, cost a model round-trip per decision and were repeatedly violated in real runs (see LESSONS 2026-11-12/13: completion attempted without evidence, QA exhausting turns, replay consuming the delegation budget). Tests were written after code by the implementer, so review spent turns disputing coverage. Follow-ups had no saved regression checks. Users judge the loop by time to first visible source, saved-version rate, wall time and follow-up cost. The research notes in [docs/research](../research/) and the sources below compare v0, crewAI, OpenAI and Anthropic guidance; all recommend code-owned workflows with structured handoffs, one writer per artifact and evaluator-optimizer loops over clear criteria.

## Decision

Use a native CrewAI `Flow` (`DeliveryFlow` in [delivery/flow.py](../../apps/backend/src/formlane/delivery/flow.py)) as the orchestrator. Each stage is one focused CrewAI `Agent` with role-scoped tools and a terminal tool. The Flow enforces stage order and acceptance; Mike directs subsequent iterations when review has not established completion.

1. **Route (Mike).** Initial builds always plan. Follow-ups make one small `choose_route` call: `quick_edit` or `plan`. Quick edit requires saved acceptance checks; otherwise the route falls back to plan.
2. **Plan (Emma and Bob).** One `submit_plan` call returns brief, A1–A8 criteria, assumptions, gaps, template, architecture and 2–12 acceptance checks. It initializes new projects. Checks are written before code and define the selector contract. The UI shows Emma's brief and Bob's architecture from this single structured result.
3. **Build (Alex).** Alex is the only writer of source and works in one ReAct loop with environment feedback: read/search, write/edit, `build_project`, `inspect_preview` (accessibility tree, console, page errors, document width, optionally after actions, viewport, clock or seed), `validate_preview`, fix, repeat. `submit_candidate` requires passing validation of the current build, or every failing check named in `check_defects` for the reviewer to judge. On the plan path he cannot change checks; a quick edit may update the saved set, which David then reviews independently.
4. **Verify (gate).** If Alex's implementation evidence matches the current build, no browser work repeats. Otherwise the harness builds and validates once without a model call. A fixed smoke check (375px render, no runtime error, no horizontal overflow) is prepended to every check set. Failures continue to David for independent assessment, including whether a check itself is defective.
5. **Review and iterate (David → Mike → Alex/David).** David reads changed and needed files, inspects the app, judges checks against the original request, runs his own validation and records a verdict. Missing implementation evidence is restored deterministically. If completion is still unmet, Mike receives the latest report, review, candidate and missing evidence. His durable `schedule_iteration` decision assigns concrete source repairs to Alex or evidence/check corrections to David. Source repair is followed by implementation validation and another independent review. An incomplete reviewer turn also returns to Mike. Repeat until current-source acceptance; a fixed repair count no longer terminates the Run.
6. **Deliver.** Completion still requires current build, Alex validation, David validation and David acceptance, bound to the exact source, artifact and check set. The saved version stores the accepted check set (`versions.acceptance_checks`) as the next follow-up's regression baseline.

Evidence semantics change in one respect: independent validation is recorded separately (`independentValidation`, bound to artifact and check-set hashes). Implementation re-validation on unchanged source therefore no longer erases David's verdict. This removes the Alex→David→Alex→David evidence dance without weakening any requirement.

Rejected terminal-tool attempts remain durable operations but surface as native CrewAI tool failures, allowing the current stage to correct its evidence before recording a result. Review acceptance errors identify missing current-build validation and unread added, modified or deleted files, including template configuration files on initial builds. Only a successfully recorded terminal result ends the stage; model and tool budgets still bound correction.

Templates now ship a small base stylesheet (layout, card, button, field, badge, screen-reader utilities). Plans and builds reuse it, so generated CSS stays proportional to scope. TypeScript and Python template snapshots and hash fixtures change together.

The integration keeps this native Flow and its three acceptance gates as the only execution path. The earlier alternative implementation called `flow-v2` remains a research comparison; that name is unrelated to the execution compatibility version assigned to the module refactor below. Its [v0 research](../research/2026-11-13-v0-workflow.md) and [CrewAI research](../research/2026-11-13-crewai-workflow.md) are retained as supporting sources.

Private candidates are checkpointed after committed source/build operations, outside nested DBOS steps. Failed or cancelled work can be inspected without becoming an accepted version. The owner API exposes only the latest eligible run's candidate while its baseline still matches the current version; completion, a replacement request or a changed baseline hides it. Downloads, history and publication continue to use accepted versions only.

## Consequences

- The successful first-pass path needs no additional coordinator call. Failed or incomplete review adds a Mike decision before each next iteration. Per-specialist model/tool allowances and individual operation timeouts remain bounded; iteration count has no fixed maximum. Cancellation, provider/infrastructure failures and lease authority remain effective.
- Stage keys are deterministic: existing `flow-v1/plan-0`, `flow-v1/build`, `flow-v1/verify-0` and `flow-v1/review-0` remain; subsequent decisions use `iteration-{round}-{attempt}`, source repairs use `review-repair-{round}`, and reviews advance their round. Cached decisions must match their stage path, and each review starts without an inherited verdict.
- The original rollout used execution version `flow-v1`. The module/configuration refactor below advances compatibility to `flow-v2` without renaming durable operations. `flow-v1`, `crew-v1` and `dbos-v1` histories remain stored but cannot run or resume on the new worker. Drain active work before switching; deployment records distinguish implemented compatibility from the currently active release.
- Migration `0004_version_acceptance_checks` was required for the original Flow rollout; the `flow-v2` refactor had no schema migration. [ADR-0016](0016-version-bound-visual-selection.md) subsequently requires `0005_selection_evidence`. Imported and earlier versions with null checks route follow-ups to plan.
- The Flow runs with `suppress_flow_events`, tracing disabled and auto-memory skipped. Stage failures are captured inside Flow methods and re-raised unchanged after kickoff so cancellation and failure codes do not depend on asyncio thread propagation.
- Per-stage model selection and streaming the plan into the UI remain outside this decision. Native image delivery and independent visual acceptance are subsequently defined by [ADR-0016](0016-version-bound-visual-selection.md).

## Deterministic browser environment

Staging run `05fa1643-67a3-43fc-a2ff-b9509ed181e1` saved a tool library that hardcoded "today" as 2026-03-18 because checks could not control time, so the plan pinned dates and the build matched them. Production style follow-ups on 2048 (`1e28f623-3fb7-4b5d-a682-bb4745b70c76`, `9edbdb6b-7ff3-47e9-9ff0-dd7f99524b2e`, `a2717c46-3673-475c-8783-ebb7723c891d`) spent 13 validations and 10 check rewrites on expectations about randomly spawned tiles and never saved. The browser environment is therefore deterministic and controllable:

- Each check may set `clock {now, timezone}`. Checks asserting calendar dates must set it, and the set must contain two different `clock.now` values, so a hardcoded date cannot pass both.
- `Math.random` and `crypto.getRandomValues` are seeded per check (`seed`, default 1) by an init script inside the sandboxed iframe. The same check observes the same random state every run; `inspect_preview` with that seed shows it.
- The first `srcdoc` document in the isolated iframe ran before Playwright's clock, timezone and init-script overrides attached (observed on the VM: at-load values were real time, UTC and unseeded). A warm-up navigation precedes every candidate load so overrides apply from the app's first script.

## Reasoning effort

The provider defaults to deep reasoning. Staging plan call `flow-v1/plan-0/llm-1` took 306 s for a 19.6 KB result. Probes on `grok-4.7` accepted `low`, `medium` and `high` with and without tools and rejected `none`. Stages set effort explicitly: router and planner `low`; builder, quick edit, repair and reviewer `medium`.

## Runtime modules, configuration and extension points

The stable entry point is [delivery.execute_harness](../../apps/backend/src/formlane/delivery/__init__.py). `delivery/flow.py` owns the native graph; `delivery/stages.py` owns Agent construction, verification and the coordinator-directed review loop. `delivery/workspace.py` owns durable operations, source/build/check evidence, candidate checkpoints, iteration decisions and completion; it alone mutates evidence stamps. `delivery/schemas.py` holds tool argument and plan models. `delivery/tools.py` declares concrete tools and ordered role capabilities. The coordinator can observe the workspace and schedule repair/review; it cannot edit source, rewrite checks or waive acceptance.

Stage policy lives in [delivery/resources/stages.yaml](../../apps/backend/src/formlane/delivery/resources/stages.yaml): persona display names/roles, resource references, reasoning effort, per-turn iteration limits, named tool sets, budgets and decide-now instructions. Adjacent text resources hold goals and work contracts, including coordinator instructions. [delivery/configuration.py](../../apps/backend/src/formlane/delivery/configuration.py) validates and caches immutable packaged configuration before worker polling; invalid configuration fails startup. Python, YAML and text changes require a new compatible release and restart. Wheel and source distributions include all declared resources.

Tool budgets use official scoped `PRE_TOOL_CALL` and `POST_TOOL_CALL` hooks in [delivery/hooks.py](../../apps/backend/src/formlane/delivery/hooks.py). PRE checks authority and validates arguments before charging the stage allowance; malformed calls preserve the budget even after exhaustion. Valid exhausted calls never reach the workspace or allocate a durable tool operation. CrewAI discards a PRE abort's custom reason, so POST relays the original decide-now JSON to the next model request, matched to the tool name and input object and cleared after that call. Counts are rebuilt as native execution replays committed tool calls. The ContextVar hook scope surrounds only `agent.execute_task`, restores the previous registry on success or failure, and isolates concurrent stages. Ordinary hook exceptions would be swallowed by CrewAI; authority failures propagate through `RuntimeAbort` instead.

Private CrewAI dependencies remain confined to [delivery/_crewai.py](../../apps/backend/src/formlane/delivery/_crewai.py). `ObservedOpenAI` synchronously observes text and raw file-argument deltas inside the durable provider call and creates a fresh observer for each retry, discarding partial fragments. Official `LLMStreamChunkEvent` handlers run inline only without event dependencies: dependency dispatch can return from the provider and outlive the durable scope on another thread, and ordinary listener errors are swallowed. A passing inline-listener example therefore does not establish the required ordering, authority or commit lifetime. The adapter also keeps `SourceExecutor` sequential even if a provider returns a batch despite `parallel_tool_calls=False`, and reuses the native Flow definition because the pinned CrewAI version discovers decorated methods on the concrete class only. Public provider calls remain individual DBOS steps; private reasoning is never exposed.

Private DBOS scheduling lives in [formlane/_dbos.py](../../apps/backend/src/formlane/_dbos.py). `durable_execution.resume_with_authority` holds the application lease lock and passes that same transaction connection to the adapter. The adapter binds the SDK system database to it and disables independent reconnect retries. The public resume API opens its own transaction, which cannot preserve this application fence after a connection failure. Dormant initial enqueue remains separate from authorized dispatch; no worker-startup DDL is introduced.

## Replay compatibility and upgrade gates

The module refactor introduced execution compatibility `flow-v2`; [ADR-0016](0016-version-bound-visual-selection.md) advances it to `flow-v3` for selection and native visual acceptance. Workflow `formlane.flow.v1` and the `flow-v1/...` durable namespace remain. Coordinator iteration deliberately changes repair ordering and adds decision steps. Source/config manifest mismatch therefore prevents old unfinished Runs from replaying under the new policy. The manifest hashes every packaged `.py`, `.yaml`, `.yml` and `.txt` file using sorted package-relative paths, excluding hidden files, bytecode and `__pycache__`; it also records library versions, model and endpoint identity without credentials, query or fragment.

The saved application manifest is compared with the current manifest under authority before scheduling or consuming a cached DBOS `SUCCESS`. A missing manifest fails closed if the workflow succeeded or has any committed operation; an empty dormant enqueue interrupted before its first step can still recover. Mismatched versions or manifests raise `ExecutionVersionMismatch`, prevent further execution and remove resume eligibility. Historical runs, events and versions are retained. Do not rewrite old manifests to make a release appear compatible.

Two executable gates in [testing](../internals/testing.md#flow-equivalence-and-library-upgrade-gates) protect this boundary: retained input scenarios with current native acceptance contracts, and installed CrewAI/DBOS contracts including real PostgreSQL recovery/fencing. The immutable `inputs.record` bytes identify golden provenance; refactors never regenerate recordings to bless changed behavior. CI runs these gates and a disjoint complete remainder of the backend suite. The library pins remain CrewAI `1.15.40` and DBOS `3.5.0`; any upgrade must pass both gates and real-provider release acceptance. Historical `flow-v2` activation and rollback use their [recorded procedure](../operations/deployment.md#runtime-module-release-flow-v2); selection's schema change has a separate [release boundary](../operations/deployment.md#visual-selection-release-flow-v3).

The user-requested iteration policy superseded four historical fixed-repair scenarios. `flow-v3` additionally changes success semantics for the eight remaining input scenarios by requiring native desktop/mobile images and explicit visual approval. Their original recording bytes remain immutable provenance; executable tests assert the new acceptance contract, multiple rejected reviews followed by acceptance, evidence-only correction, stage-stamped decisions and cancellation/replay. Changed behavior is tested explicitly rather than captured as a new golden.

## Alternatives

| Option                                              | Reason not selected                                                                                                                     |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Keep the hierarchical Crew and refine prompts       | Real-provider runs kept violating prompt-encoded routing; crewAI positions Flows as the production control layer                        |
| Plain Python state machine without `Flow`           | Equivalent control, but the user asked to follow crewAI's official practice; `Flow` adds a declared, plottable graph at negligible cost |
| Parallel specialists writing source                 | Conflicting implicit decisions (Cognition); one writer remains                                                                          |
| Save after deterministic verification, review later | Rejected by the user: every saved version keeps independent review                                                                      |
