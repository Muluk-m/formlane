# DBOS durable node recovery

Status: accepted. This replaces the custom execution-replay authority in ADR-0013 while retaining FastAPI, native CrewAI, PostgreSQL, and static Pages. The former retry action created a new run and abandoned committed model/tool checkpoints; recovery must instead continue the existing execution.

Use pinned DBOS with PostgreSQL to record each completed model request and tool operation. CrewAI remains the orchestration framework; wrapping a whole crew or specialist in a DBOS step would hide its internal operations and is explicitly insufficient. Application ownership, project selection, progress watchdogs, lease fencing and immutable-version acceptance remain authoritative business constraints around the durable workflow. A resume is an authorized new attempt of the same run, not a new user request. Completed, superseded or baseline-invalidated runs cannot be resumed.

The fixed 15-minute total attempt budget interrupted a real acceptance-check repair despite recent committed work. Queue waiting now has no deadline. First claim starts a 15-minute inactivity watchdog; only a newly committed model/tool checkpoint renews it. Cached results, streamed events, lease heartbeats and automatic running-job reclaim cannot keep stalled work alive. Total execution may exceed 15 minutes while progressing. Per-call timeouts, bounded repairs/retries, cancellation and independent acceptance remain enforced.

Completed operation results and source/evidence snapshots are reused. Interrupted operations without committed results may execute again, including provider billing; neither DBOS nor a local checkpoint can promise exactly-once effects in an external model provider. Workflow compatibility is pinned across recovery. Legacy checkpoints are deliberately consumed into the new execution history, not discarded. Changed execution semantics require an explicit migration or the matching previous worker release.

DBOS history and application state use separate schemas in the same PostgreSQL database. The pinned SDK's public resume retries on a separate connection, which cannot share the application lease fence. A small per-call adapter binds its unchanged scheduling operation to the lease transaction and disables independent reconnect retries. Initial creation uses an unconsumed queue; only the fenced transaction dispatches work to a producer's private queue. SDK upgrades must revalidate this adapter with connection-loss and process-death tests.

CrewAI 1.15.40's native snapshot providers are local JSON/SQLite and its standalone restore path does not establish the required PostgreSQL recovery guarantee. Temporal is a viable durable engine, but adds a separate workflow service where DBOS uses the existing PostgreSQL deployment. DBOS still requires explicit schema migration, durable step boundaries, deterministic replay, idempotent effects and process-interruption acceptance.
