# Testing strategy

## Scope and coordination

One integration owner runs authorized checks after shared edits land. Select explicit relevant test files and package typechecks; avoid overlapping installations, full builds, suites or watch processes. Delegated editing alone does not authorize verification. Test existence, historical screenshots and HTTP availability do not establish migrated production acceptance.

For local changes, run `pnpm check:changed` from the repository root (or pass an explicit base ref). It checks staged evidence paths, runs Biome on supported changed files, typechecks affected JavaScript packages and selects nearby tests. Python selection covers changed test files and matching top-level backend modules; nested `delivery/` changes still require explicitly selecting their relevant behavior gates below. Documentation-only changes need link/command review; this gate does not validate Markdown links.

[JavaScript CI](../../.github/workflows/checks.yml) runs on every pull request and pushes to `main`/`test`, including documentation changes: tracked-evidence guard, lint, typechecks, tests and build. [Python CI](../../.github/workflows/python-checks.yml) covers backend/compiler/web and their shared core/contracts/UI/i18n dependencies, the pnpm lockfile and its own workflow; a docs-only PR does not trigger it. It also runs real browser compiler, Preview runtime and provisioned workspace scenarios. A merge does not deploy either runtime; releases use the separate [deployment workflow](../operations/deployment.md#routine-frontend-release).

## Behavior boundaries

| Boundary             | Required coverage                                                                                                                                                                                                                                                         |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API/ownership        | Contract-compatible JSON/errors; preserved owner header; private project/chat/version/download isolation; explicit allowed/denied CORS origins                                                                                                                            |
| Provider/CrewAI      | Flow stage order, coordinator-directed iteration past former repair limits, per-stage tool budgets and reasoning effort, role-scoped tools, streaming, missing-key/provider failures and no mock fallback                                                                 |
| PostgreSQL           | Explicit empty-database Alembic migration, constraints, atomic pointer/run transitions and concurrent lease fencing                                                                                                                                                       |
| Generation           | Current-source build and check-set evidence; implementation and independent validation/review; repair, safe failure categories and prior-version preservation                                                                                                             |
| Durability           | Cursor replay/deduplication, disconnect without cancellation, explicit cancel, lease expiry/reclaim, DBOS operation replay, stale late-write rejection and bounded individual operations                                                                                  |
| Source/compiler      | Cross-runtime source/hash fixtures, fixed templates, virtual imports, size/time/output bounds, stripped credentials and cancelled process cleanup                                                                                                                         |
| Browser isolation    | Native sandboxed Chromium, opaque iframe, network/WebSocket denial, declarative interaction/assertions, pinned clock/timezone at two moments, seeded randomness effective from the first app script (warm-up navigation), observation-only inspection and repair evidence |
| Versions/publication | Monotonic numbering, inspection without mutation, restore, ancestry-based Undo, independent remix, exact ZIP, frozen publication, republish and unpublish                                                                                                                 |
| UI                   | Query invalidation, draft retention, localized errors, keyboard/focus behavior, desktop/mobile layout and SPA reload                                                                                                                                                      |
| Static cutover       | Direct API origins, unchanged owner capability, old-client 307 method/body forwarding, public-link 302, SSE reconnect and origin-specific CORS                                                                                                                            |

Use the lowest boundary that reproduces the behavior. Extend existing cases rather than mirroring implementation or asserting only mocked calls. Database behavior needs real PostgreSQL locks/transactions. Backend fixtures require `TEST_DATABASE_URL` and isolate schema state in a dedicated test database. Keep the remote `formlane_test` database separate from stage and production.

Backend tests live in [apps/backend/tests](../../apps/backend/tests/); compiler tests in [apps/compiler/src](../../apps/compiler/src/); frontend/package tests remain alongside their modules. Use named pytest files from the backend environment and guarded named JavaScript tests. Inject time where possible; intercepted model HTTP is deterministic boundary coverage, not real-provider acceptance.

Browser tests require a sandbox-capable Chromium/Chrome compatible with Python Playwright. Select it through `BROWSER_EXECUTABLE_PATH` when needed. Preserve non-root execution and the sandbox; on Ubuntu, account for the host's AppArmor/user-namespace policy instead of adding `--no-sandbox`. Compiler and browser descendants must lose provider/database credentials and terminate on cancellation.

Python CI pins Ubuntu 24.04 and Google Chrome `156.0.8078.79`, matching the isolated acceptance/runtime browser. It downloads that exact official Debian package, verifies the executable version and prepares its files before every browser-capable gate, including recorded acceptance and DBOS recovery. Reading the browser bundle materializes cold runner-image pages: measured first launches otherwise spent seconds blocked on executable-page disk reads. The step preserves the browser's existing AppArmor profile, non-root sandbox and executable selection. It does not launch a warm-up browser, retry a failed launch, increase a timeout or change acceptance assertions. Browser/Playwright upgrades require the full browser regression suite and real workspace qualification; a successful launch alone does not establish iframe-validation compatibility. Chrome `157.0.8103.50` remains unqualified after intermittent scene, random-state and outline-pixel failures.

## Flow equivalence and library upgrade gates

The two approved seams are the public [delivery.execute_harness](../../apps/backend/src/formlane/delivery/__init__.py) entry point and the installed CrewAI/DBOS runtime. Use the prepared backend environment, a built compiler, sandboxed Chrome and an isolated PostgreSQL database through `TEST_DATABASE_URL`. From the repository root, the owner can run each gate explicitly:

```bash
# Gate 1: frozen input scenarios with current native acceptance and iteration contracts.
uv run --project apps/backend pytest apps/backend/tests/test_flow_equivalence.py apps/backend/tests/test_iteration.py

# Gate 2: installed-library behavior plus real DBOS recovery and compatibility.
uv run --project apps/backend pytest apps/backend/tests/test_runtime_contract.py apps/backend/tests/test_durable_execution.py apps/backend/tests/test_execution_compatibility.py
```

Gate 1 executes eight retained scenarios: initial build, quick edit, plan follow-up, disputed check, tool-budget exhaustion, missing key, cancellation and resume reusing committed operations. Their inputs and the twelve original [recordings](../../apps/backend/tests/fixtures/flow_equivalence/) remain immutable provenance from `af5e54f`; `inputs.record` retains SHA-256 `f433e43bc356abbdec48a443704641a308cabe2f947b72e54751c1efa8d1a000`. `flow-v3` deliberately replaces acceptance without images with native desktop/mobile image receipt and explicit visual approval. Executable scenarios assert those new semantics and existing source/behavior invariants rather than claiming byte-for-byte equivalence to the old outputs. The four fixed-repair recordings remain historical; iteration contracts prove eventual acceptance after multiple negative reviews, evidence-only correction and cancellation/replay without repeated committed effects. Never regenerate recordings to bless changed behavior.

Only external provider transport, compiler/browser outcomes, time/identity/randomness and the in-memory durable journal are controlled in recorded-scenario replay. The real Flow, stages, workspace, tools, native executor and model-call boundary execute. These contracts establish deterministic harness behavior, not live-provider acceptance or real database recovery.

Gate 2 uses CrewAI `1.15.40` and DBOS `3.5.0` as installed. Native contracts prove raw file deltas precede tool execution, retry fragments reset, ordinary nonterminal tool batches stay sequential on the provider thread, PRE can block without executing a tool, POST relays the exact reason, and authority aborts stop execution. They also characterize why official stream listeners are not adopted: dependency dispatch can finish after provider return and the live durable scope, while ordinary listener errors are swallowed. The safe inline case and unsafe dependency case are both executable contracts, not skipped tests or a blanket listener guarantee. Application budget/lifecycle regressions in `test_agents.py` exercise invalid arguments without budget consumption, normal/abort cleanup, concurrent stage isolation and replay without repeated effects.

The PostgreSQL/DBOS cases exercise actual process death, dormant enqueue before dispatch, committed-operation reuse, same-run/new-attempt resume, scheduling-connection termination, replacement-lease fencing and cancellation of old producers. Compatibility cases cover `flow-v3` eligibility and retained but non-resumable older execution versions; portable sorted manifests of all packaged Python/YAML/YML/text files; credentials/cache exclusion; and source/resource additions, changes and removals. Drift or missing manifest evidence blocks unfinished replay and cached `SUCCESS` completion without repeating effects. Missing evidence after committed work fails closed, while an empty dormant enqueue remains recoverable. Durable names remain `formlane.flow.v1` and `flow-v1/...`, including the candidate reader. Do not substitute the in-memory scenario journal for these database tests.

[Python CI](../../.github/workflows/python-checks.yml) partitions backend collection into four disjoint steps: recorded acceptance scenarios plus iteration contracts; native CrewAI contracts; DBOS recovery plus execution compatibility; and the complete `apps/backend/tests` root excluding exactly those five named files. The remainder includes configuration/startup, application hooks, model streaming, selection inspection/evidence, validator, storage, worker and API tests; future backend test files are included automatically. Separate steps run compiler/Preview browser boundaries and the owned workspace suite below. No file runs twice across these steps. Both gates must pass before a library bump or replay-affecting refactor; the full remainder and normal lint/compiler gates remain required. CI configuration alone is not evidence of a green candidate run.

Configuration coverage in `test_configuration.py` checks malformed resources fail before worker polling and loaded policy stays immutable/cached. Packaging verification must load every declared resource from both wheel and source distribution, including a fresh interpreter loading configuration from the wheel, not only a source checkout. Prompt wording assertions are not a substitute for the frozen gate, iteration contracts or real-provider acceptance.

The configuration suite also reuses the native recording observation helper for initial builds and quick edits, checking that a customized Mike display name reaches both entry-point lifecycle events. Recording provenance stays fixed while current acceptance assertions explicitly include native image delivery.

## Visual selection boundaries

The primary feature seam is the owned workspace: load an accepted Version, operate its live scene, enter Edit, select through pointer/ancestors/Layers or a region, submit a comment, observe independent acceptance and Undo through generation ancestry. Deterministic browser fixtures live under `apps/web/tests/fixtures`; captured output stays outside the checkout.

```bash
uv run --project apps/backend pytest apps/compiler/tests/test_editor_artifacts.py apps/web/tests/test_preview_selection.py
uv run --project apps/backend python apps/web/tests/run_selection_workspace.py
```

The workspace runner requires the built compiler, installed workspace dependencies, sandboxed Chrome and `TEST_DATABASE_URL` naming a dedicated `formlane*_test` database. It reuses the existing PostgreSQL schema fixture, compiles a deterministic application, seeds two Versions with real generation ancestry, builds the frontend against an isolated loopback API, and starts only its own API/preview processes. It supplies `FORMLANE_SELECTION_PROJECT_URL` and `FORMLANE_SELECTION_OWNER`; missing fixture configuration fails in CI. No worker or provider runs in this deterministic suite. Service logs are private temporary files outside the checkout; processes and the temporary schema are cleaned up on success or failure.

Controlled-provider cases cover immutable selection recovery, exact/heuristic/ambiguous/missing target outcomes and rejection of client, baseline, stale or wrong-stage images as current acceptance. Browser fixtures exercise canonical/editor parity, event suppression, document replacement, live modal/form preservation, Layers, regions, stale/uncertain submissions, history and localized mobile UI. The workspace fault cases intercept HTTP at the transport boundary; they do not claim model-generated completion.

Real-provider acceptance separately covers both Templates and hero typography, nested span-to-heading selection, one repeated occurrence, an explicitly shared change, an open modal and a planned behavior change. Exercise every accepted result and functional Undo, retained publication, same-run recovery and immutable original evidence. Record exact release/Run/Version identities, first-file time, wall time, committed model calls, repairs, resolution failures and collateral edits. Native capture requires a headed browser and real chooser/crop behavior; permission denial, wrong surface, scrolling/zoom and selected pixels must be observed. Neither a mocked stream nor deterministic fixture success establishes native capture or real-provider acceptance.

## End-to-end evidence

A real-provider acceptance pass covers idea → plan/build/verify/review Flow → validated saved preview → follow-up → history/restore/Undo → remix/download → publish/republish/unpublish → reload. Separately exercise reconnect, cancellation, individual operation timeouts and restart/reclaim with the current deployed backend. Healthy execution and queue waiting have no whole-run deadline; long-running work must retain renewable lease authority. Record release, run/version identity and observed result; a successful tool probe is narrower evidence.

UI evidence checks actual rendering, both locales, dialogs/focus, status treatment, source comparisons, 375px layouts and unsent drafts. Generated apps may use their requested visual style; the shell retains Skyline.

[Deployment](../operations/deployment.md) owns current release identities, completed Python/PostgreSQL cutover evidence and cleanup verification. Record results against the exact candidate and database; historical targeted test counts do not establish acceptance of a later release. Distinguish an eventual green CI run from a fix for intermittent browser failures.
