# Formlane: CrewAI and coding-workflow research

Access date for every source below: **2026-11-13**. Research is read-only; no repository source changes, executions of downloaded projects, builds, tests, formatters, paid model generations, production mutations, or messages to external parties were performed.

## Decision supported by the evidence

**[RECOMMENDATION] Keep DBOS as the durable execution owner; replace the open-ended managerial control loop with explicit application stages and bounded coding/repair work. CrewAI can remain a worker implementation.** A framework replacement is not necessary to obtain typed state, deterministic routing, executable gates, or explicit repair limits. CrewAI itself recommends a Flow-first architecture, focused Crews, explicit inputs, structured outputs, and guardrails [C1]. LangGraph and OpenHands provide useful design references, but installing either would not by itself fix missing artifact commits or validation stages.

**[USER-REPORTED FACT]** The neighbor-tool-library project exposed zero versions and ended at `step_limit`, initially appearing to stop before validation/review. **[PARENT-SUPPLIED LOCAL EVIDENCE; NOT INDEPENDENTLY RE-QUERIED HERE]** The main retrospective subsequently established CrewAI **1.15.40**, DBOS **3.5.0**, Python **3.13**, and **96 checkpoints** for the failed request. An artifact passed eight independent checks and received accepted review, but delivery lacked a builder-specific validation record. The manager then re-delegated to the product analyst, whose revised brief added a mandatory no-persistence disclaimer. The same artifact later passed ten checks and was rejected solely for the absent disclaimer before `step_limit`. Current role instructions prohibit network, backend, and browser storage. These facts refine the initial symptom: useful work and review existed, while role-specific delivery requirements and a changed brief prevented an accepted version. The main report owns the underlying local citations. The exact application counter behind `step_limit` is not established by this public-source research and must not be automatically equated with CrewAI `max_iter`.

**[INFERENCE]** A workflow in which a manager must keep choosing to delegate, inspect, validate, review, and finally save makes mandatory product milestones compete with discretionary agent reasoning. Raising a single limit can postpone the same failure. The stronger intervention is to make artifact persistence and validation mandatory transitions owned by application code, with model autonomy inside bounded implementation work.

**[INFERENCE FROM LOCAL EVIDENCE]** The strongest diagnosis is a broken acceptance protocol: evidence is attached to role ceremony rather than to the artifact and the agreed contract, and a later role can move the acceptance target after review. Ninety-six checkpoints show recorded activity, not delivery progress. The remedy is neither simply more checkpoints nor a larger iteration budget. A fixed capability/spec contract and reusable artifact-bound validation evidence address the observed chain directly.

## 1. What CrewAI actually supplies

### Structured state and routing

**[SOURCE EVIDENCE]** `Flow[StateModel]` accepts Pydantic state; `@start`, `@listen`, `@router`, and logical conditions support event-driven sequencing, branches, and loops. Routers can return declared `Literal` labels. The production guide explicitly says to start with a Flow and pass necessary state into focused Crews [C1, C2]. These are real framework capabilities, not a need to simulate a state machine through manager prose.

**[SOURCE EVIDENCE]** Tasks support `context`, `output_pydantic`, and `output_json`. Task outputs default to raw text; the docs explicitly say typed fields can be `None` when conversion fails [C3]. A configured schema is consequently not evidence that a valid typed result was obtained. Reject missing/invalid typed output at the application boundary. Schema validity also says nothing about whether the referenced files exist or compile.

**[SOURCE EVIDENCE]** Hierarchical execution supplies a manager that delegates and evaluates worker results. Documentation still describes sequential task progression; the presence of a manager is not a documented guarantee that all desired engineering stages will be run [C4]. At the inspected source revision, the agent executor itself is implemented using Flow state containing messages, iteration counts, plan state, and observations [C6]. This is a runtime implementation detail, not a reason to expose its internal plan as Formlane's product state.

**[RECOMMENDATION]** Use a narrow, versioned product state: `run_id`, `workflow_version`, `request_revision`, `spec_ref`, `workspace_snapshot_ref`, `candidate_id`, `artifact_hash`, `phase`, `validation_ref`, `review_ref`, repair history, budgets, and terminal reason. Keep large files/logs/screenshots in an artifact store and retain references in state. Store implementation progress and accepted product versions separately. Never derive completion from the last natural-language agent message.

### Guardrails and repair boundaries

**[SOURCE EVIDENCE]** CrewAI supports deterministic function guardrails and string guardrails evaluated by an LLM. Guardrails validate/transform task output. Multiple guardrails run sequentially, and a failing guardrail can rerun the agent up to `guardrail_max_retries` (documented default 3) [C3]. The inspected `Task._invoke_guardrail_function` uses `guardrail_max_retries + 1` validation attempts, constructs retry context from the validation error and prior raw output, and invokes `agent.execute_task` again [C7]. This is additional agent work; it is not a bounded compiler repair transaction supplied automatically by the framework.

**[INFERENCE]** Several independent retry layers can multiply work: provider transport retries, agent error retries, task guardrail retries, application repair attempts, and DBOS step retries. The exact count is execution-path dependent; a simple universal multiplication formula would be misleading. A limit at one layer does not bound the whole run.

**[RECOMMENDATION]** Use cheap guardrails for schema, nonempty artifact manifests, correct base revision, permitted paths, and required evidence references. Run compilation, browser journeys, and review as explicit stages with typed outcomes. Give transient infrastructure failures a different policy from a failed application check. A compile error should become a repair input, not automatically restart an entire Crew through a generic exception retry.

### `max_iter` is an exhaustion boundary, not a quality certificate

**[SOURCE EVIDENCE]** Agent documentation describes `max_iter` as maximum iterations before providing the best answer, default 20 [C5]. In the inspected source revision, `has_reached_max_iterations` checks `iterations >= max_iterations`. `handle_max_iterations_exceeded` appends a forced-final-answer instruction, makes another LLM call, and returns `AgentFinish`; the helper can retry an empty response. The executor routes either max-iteration exhaustion or its repeated-tool-call limit to this forced-answer path and sets `is_finished = True` [C6, C8]. Thus a normal-looking final answer can be produced after exhaustion without the implementation being validated.

The internal executor field observed in source defaults to 25, whereas public Agent docs say 20 [C5, C6]. Do not use the internal constructor default to infer an actual Agent's configured budget. Inspect Formlane's pinned dependency and passed values. Recent source contains planning/native-tool paths, so iteration count is not safely interchangeable with the number of tool calls, model requests, delegated tasks, or product phases.

**[RECOMMENDATION]** Preserve exhaustion as a machine-readable result, even if CrewAI returns a final string. A worker result should distinguish `candidate_produced`, `needs_context`, `blocked`, and `budget_exhausted`. An accepted application version requires artifact-bound validation independently of that result. Reserve downstream validation/save capacity; do not let the planner or worker consume the entire end-to-end budget.

### Delegation does not carry an implicit complete project

**[SOURCE EVIDENCE]** `DelegateWorkToolSchema` requires three strings: `task`, `context`, and `coworker`. The implementation finds a coworker by role, creates a new Task with the delegated description and a generic manager-request expected output, then calls `selected_agent.execute_task(new_task, context)`. Exceptions are converted into tool error strings [C9]. This boundary does not itself forward the parent's complete transcript, original task guardrails, output schema, or acceptance contract. A configured worker may separately have memory, knowledge, and tools; the source does not justify saying the worker has literally no other context.

**[RECOMMENDATION]** Replace informal managerial delegation on the critical path with application-built work packets: task ID, goal, relevant spec clauses, current artifact hash, allowed write set, exact tool contracts, dependencies, relevant prior diagnostics, acceptance criteria, and budget. Require an artifact reference plus a typed status, not a narrative handoff that rewrites the code through the manager. This follows Anthropic's documented requirement for clear objective, output format, tools, boundaries, and artifact references [A2].

### Persistence: distinguish state hydration, checkpoints, and external effects

**[SOURCE EVIDENCE]** CrewAI `@persist` saves Flow state after persisted methods complete, with SQLite fallback/custom persistence support [C2, C10]. Its current docs distinguish deprecated `inputs={"id": ...}` hydration extending an existing lineage from `restore_from_state_id` hydration into a fresh lineage; the latter is a fork, not a transparent same-run resume [C12]. The Flows page says an unknown restore ID silently falls back. An application needing strict recovery should reject an absent source explicitly rather than treating this as a recovered run [C2].

**[SOURCE EVIDENCE]** Current CrewAI also has a separate, fuller **checkpointing** facility for Crew, Flow, and Agent. It captures configuration, task progress, intermediate outputs, state, inputs, events, and lineage; completed tasks can be skipped on restore. Default checkpoints occur at `task_completed`, with higher-frequency events available; JSON and SQLite providers ship [C11]. It would be incorrect to summarize today's CrewAI as having only state snapshots and no resumable execution.

Material restore caveats are documented: automatic checkpoint writes are best-effort and log failures; manual checkpoint calls re-raise. Restore reconstructs the saved object, not the caller's modified object. Named module-level callbacks require trusted deserialization opt-in; closures/lambdas/bound callbacks are not retained; **callable guardrails are not saved**, while string guardrails are; `@CrewBase` before/after kickoff hooks are not restored [C11]. **[INFERENCE]** Restoring without reconstructing deterministic validation requirements can weaken a supposedly guarded pipeline. Keep mandatory gates in the durable application workflow, or explicitly reattach and verify them.

None of these cited guarantees establishes an atomic commit spanning a model request, sandbox file mutation, external browser process, Formlane database version, and CrewAI checkpoint. Framework state and workspace state must be reconciled deliberately.

## 3. First-party guidance that changes the design

### LangGraph

**[SOURCE EVIDENCE]** LangGraph's Graph API makes shared typed state, work nodes, and fixed/conditional edges explicit; `Send` supports dynamic fan-out and `Command` combines updates with routing. Reducers define how concurrent updates merge [L1]. Its docs distinguish thread checkpoints from long-term stores [L2]. Nodes checkpoint at super-step boundaries, and a node may rerun from its beginning after retry/interrupt. Side effects therefore need idempotency. Completed functional tasks can be cached within a node/entrypoint [L1].

**[RECOMMENDATION]** Borrow explicit transitions and state contracts. Do not add a second graph persistence engine just to get conditional logic that ordinary Python inside DBOS already supports. If LangGraph is adopted later, define whether it or DBOS owns each recovery boundary, how checkpoint IDs map to run/candidate IDs, and how external effects are reconciled.

### Anthropic: long-running coding and role overhead

**[SOURCE EVIDENCE]** Anthropic distinguishes predefined workflows from model-directed agents and advises adding complexity only when measured benefits justify cost/latency. It recommends environment-grounded feedback, stop conditions, and verifiable coding outcomes [A1].

Its long-running coding write-up reports that compaction alone was insufficient. The successful experimental harness used an initialization session, a structured feature list, incremental feature work, progress artifacts, and browser-based end-to-end verification. The initializer and coder were different prompts over the same harness, tools, and system prompt—not evidence that two permanent autonomous roles are necessary. The author explicitly leaves open whether single-agent or multi-agent coding performs best [A3]. The demonstration's 200-plus features should not be copied into a small Formlane request; acceptance decomposition must remain proportional to the user's actual scope.

The multi-agent Research article reports about 4× chat tokens for agents and 15× chat tokens for multi-agent systems in Anthropic's data; **15× is versus chat, not versus a single coding agent**. It says coding often has fewer independent parallel subtasks than research and describes dependency-heavy shared-context work as a poor fit. Its 90.2% research-evaluation improvement is not an app-generation benchmark [A2].

**[RECOMMENDATION]** Start with one implementation owner, deterministic validation, and a separate evidence-based review pass. Add specialists only for an identified independent slice or a failure class where evaluation shows benefit. An architect/planner, coder, QA, chief QA, and manager chain should not be the default just because those labels resemble a human organization.

## 4. Recommended workflow primitives

All items in this section are **[RECOMMENDATIONS / DESIGN INFERENCES]**, grounded in the sources above rather than claimed properties of current Formlane.

1. **An immutable request/spec revision.** Capture intended behavior, routes, data operations, visual constraints, and testable user journeys. Permit clarification only for genuinely blocking information. Record assumptions. Do not let repair silently rewrite acceptance criteria.
2. **A deterministic lifecycle.** `prepare → implement → persist_candidate → validate → [repair → persist_candidate → validate]* → review → commit_accepted_version`. Reviews that cause edits return through validation. Every stage also has explicit failure/cancel/exhaustion exits. `validate` cannot be skipped by a manager's final answer.
3. **One mutable workspace owner.** Worker edits must identify a base snapshot. Parallel work, where justified, uses isolated snapshots/write sets with deterministic integration. Validators and reviewers inspect a frozen candidate; mutations create a new candidate and invalidate prior evidence.
4. **Small artifact-backed worker results.** Return candidate hash, manifest, changed paths, completed spec clauses, known blockers, and termination reason. Code and full diagnostics live in artifacts. The workflow checks artifact existence instead of trusting prose.
5. **A validation contract.** Return `passed`, `failed`, or `infrastructure_error`, plus candidate hash, environment/toolchain identity, check IDs, exit codes, normalized diagnostics, and browser evidence. Compilation and relevant runtime/browser journeys are separate gates. A preview URL alone is insufficient evidence.
6. **Bounded repair with a progress record.** Persist each repair's input candidate, diagnostic fingerprint, patch hash, output candidate, and gate results. A repeated candidate/error pair or A→B→A cycle triggers a different bounded strategy or a clear terminal failure, rather than indefinite re-delegation. Rank failures by gate/severity and criterion coverage; raw compiler error counts alone are not a convergence metric because fixing an early error can reveal later ones.
7. **Budget partitions.** Separately cap reasoning/tool work, repair attempts, transient retries, elapsed time, and spending, including all nested calls. Reserve enough capacity to persist current progress and execute mandatory validation. Choose numerical thresholds from representative evaluations, not an unsupported universal magic number.
8. **Explicit accepted versus incomplete output.** Persist every recoverable candidate before validation, but label it incomplete/unvalidated until gates pass. If a user-visible “version” means validated output in Formlane, preserve that meaning. Fix zero-artifact loss through draft/candidate persistence rather than silently weakening the version acceptance contract.
9. **Independent review with concrete findings.** Give review the exact frozen candidate, spec, and validation evidence; require blocker IDs tied to observable violations. Do not require a succession of free-form “looks good” approvals. Review does not override a failed deterministic gate.
10. **A terminal result the UI can explain.** Distinguish success, validation failure, blocked dependency, infrastructure failure, user cancellation, and budget exhaustion. Surface saved candidate/recovery context and the last completed mandatory milestone. “Agent finished” is not a product success state.

These primitives preserve open-ended coding decisions inside implementation while making delivery obligations predictable.

### Capability contract and evidence reuse for the observed failure

**[RECOMMENDATION]** Before asking a planner to describe an app, construct a machine-readable capability contract from what the execution environment actually supports. Include rendering/runtime constraints, outbound network policy, server API availability, browser persistence modes, durable data availability, authentication availability, and deployment constraints. Pair each user requirement with `supported`, `requires_provisioning`, or `unsupported` plus a reason. This must describe real capabilities; changing a prompt cannot manufacture a backend or a database.

For a shared neighborhood tool library, distinguish an in-session demonstration from persistent listings, reservations, users, and shared inventory. **[INFERENCE]** If the requested behavior needs shared durable data while every network/backend/browser-storage path is prohibited, the runtime contract and product promise are incompatible. The system must expose that limitation before implementation, offer an explicitly agreed demonstration scope, or provision the real capability through an authorized delivery path. It must not silently substitute a transient demo and later treat an added disclaimer as the only remaining functional requirement.

If the current product intentionally permits only transient demonstrations, required disclosure belongs to the initial accepted contract. An analyst cannot introduce it mid-repair as though it had always been an acceptance criterion. A newly discovered material limitation should be recorded as a contract-change event with provenance and an explicit impact decision; the old candidate and old evidence remain associated with the old revision. A genuine omitted user requirement also needs a transparent correction, rather than silently rewriting history.

**[RECOMMENDATION]** Represent validation evidence as `(artifact_hash, spec_revision, capability_contract_revision, validator_version, environment_identity, check_results)`. The issuer's role is audit metadata. Delivery should consume this evidence when it satisfies the required check contract, regardless of which agent invoked the validator. If builder-specific validation checks something genuinely different, name the missing check and run that check. Do not restart product analysis or repeat equivalent checks merely to obtain a different role's stamp.

Likewise, reuse accepted review only while its artifact and contract match. Eight passing checks and ten passing checks cannot be compared by count alone: preserve check identifiers, requirement coverage, and semantic results. An added disclosure criterion is a spec revision, not evidence that the unchanged executable became worse. A stale or incomplete validation record can require narrowly scoped new evidence, while an unchanged complete record should remain valid. This design follows the explicit state/gates in CrewAI's production guidance [C1, C13] and Anthropic's end-state evaluation guidance [A2]; the exact evidence tuple is this report's recommendation.

For the observed sequence, the expected replacement behavior is: recover the candidate and accepted review; resolve whether the missing builder record represents a real missing check or equivalent evidence; execute only genuinely missing checks; commit if the original contract is satisfied. If the no-persistence disclosure corrects a real undisclosed limitation, open a recorded contract correction and produce a new candidate with that disclosure, then rerun affected checks. Neither route loops back through open-ended product reanalysis.

## 5. DBOS migration implications

**[SOURCE EVIDENCE]** DBOS workflows must be deterministic given recorded step results: nondeterministic operations belong in steps. Completed step results support recovery. Step outputs must be serializable. Steps called within another step become part of the outer step rather than independently checkpointed steps; workflows cannot be started from inside a step [D1, D2].

**[RECOMMENDATION]** Keep the outer workflow as explicit Python transitions over serializable results. Model calls, reads of mutable workspace/database state, sandbox commands, browser work, artifact writes, and clock/random operations need intentional durable boundaries. If the entire Crew kickoff is one DBOS step, merely decorating its tools as nested steps does not produce independent DBOS recovery points [D2]. Choose either bounded restartable worker sessions against immutable snapshots, or expose individual worker turns/tool actions to the outer durable scheduler. The latter is more invasive and should be justified by recovery/cost needs.

**[INFERENCE]** A crash after an external operation succeeds but before its result is durably recorded can cause re-execution. Use operation IDs and reconcile external effects: content-addressed artifact writes; unique constraints for candidate/version commits; sandbox job IDs with queryable completion; a base revision on file patches. DBOS workflow-ID deduplication is valuable but does not make every external effect inside a step atomic [D1, D2]. Do not promise exactly-once LLM billing when the model provider lacks a suitable idempotency/reconciliation mechanism.

**[RECOMMENDATION]** Avoid independent DBOS plus CrewAI auto-resume authorities for the same run. If CrewAI checkpoints are retained for inner-worker recovery, store their identity/hash and committed boundary in the DBOS result, make them trusted artifacts, reconstruct omitted guardrails/callbacks, and verify that workspace state matches the checkpoint. Do not restore a checkpoint independently while DBOS believes a different candidate owns the stage.

**[SOURCE EVIDENCE]** DBOS identifies changing step calls/order as a breaking workflow change. Its supported approaches are patch markers or application versioning; versioning recovers only matching versions and recommends new-version routing while older workers drain old runs [D3].

**[RECOMMENDATION]** For a first-principles rewrite, use a new workflow/application version and preserve the old interpreter for in-flight histories. Keep legacy code only for old-run recovery until those runs are resolved; new requests use the new workflow. Do not replay an old step history through the new stage sequence. A failed old run may seed a _new_ run from a verified artifact with explicit provenance; that is migration/forking, not a pretend same-run resume. No production migration is performed by this research.

Suggested migration contracts are: versioned request/state schemas; old→new artifact import mapping; unique run/attempt/candidate identities; registered serializable stage result types; explicit cancellation and terminal-state behavior; reconciliation for an expired sandbox; and an atomic accepted-version commit tied to current validation evidence. Formlane's DBOS **3.5.0** pin is parent-supplied local evidence. Its queue configuration, checkpoint contents/size, and available migration facilities remain **[PRIVATE UNKNOWN]** here. DBOS links describe current documentation; do not assume every newer convenience API, especially patching/auto-upgrade features, exists in 3.5.0. Application-version compatibility must be resolved against the pinned package before implementation.

## 6. Acceptance criteria for the later implementation

These are proposed engineering acceptance criteria, **not tests run during this research**.

| Criterion                     | Observable pass condition                                                                                                                                                                                                                                                                                            |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Mandatory validation          | Every candidate that can reach accepted-version commit has a validation result for that exact hash. An agent final answer, guardrail string, or limit exhaustion cannot bypass the stage.                                                                                                                            |
| Recoverable progress          | After first completed implementation work, a candidate artifact and manifest survive worker failure even when no accepted version exists.                                                                                                                                                                            |
| Explicit exhaustion           | Exhausting worker or run budget yields a typed non-success terminal state, saved progress, and a precise reason. Validation/review completion is never fabricated.                                                                                                                                                   |
| No context loss at handoff    | A delegated worker can identify spec revision, base candidate, allowed scope, diagnostics, tools, and completion criteria from its packet/artifacts without relying on manager memory.                                                                                                                               |
| Repair convergence            | An injected repeated-error/no-change loop and an A→B→A regression terminate within configured bounds; the history records why the strategy changed or stopped.                                                                                                                                                       |
| Evidence invalidation         | A post-validation mutation cannot reuse the old pass result. A post-review repair is validated and reviewed as required against the new hash.                                                                                                                                                                        |
| Crash recovery                | Crash points before/after model result storage, sandbox mutation, candidate persistence, validation persistence, and accepted-version commit preserve state and avoid duplicate logical candidate/version commits. Ambiguous provider calls are reported honestly.                                                   |
| Resume policy integrity       | If CrewAI checkpoint restore is enabled, function guardrails and callbacks needed for correctness are restored/reconstructed or application gates still enforce the invariant. Missing snapshots fail explicitly.                                                                                                    |
| Deployment compatibility      | An old in-flight DBOS history recovers under compatible code; new requests run the new sequence; no old history is replayed through reordered steps.                                                                                                                                                                 |
| Race handling                 | Concurrent user revisions and stale worker responses cannot overwrite a newer project head; candidate commits validate their expected base revision.                                                                                                                                                                 |
| Failure classification        | Infrastructure unavailability does not become a code-repair diagnosis; application-check failure does not trigger an unbounded transport retry.                                                                                                                                                                      |
| Quality and efficiency        | Representative creation and edit cases—including neighbor-tool-library—are compared on full requirement coverage, accepted-version rate, time to first recoverable candidate, total tokens/cost, repair count, and human-visible correctness. Role additions must improve a stated metric under a comparable budget. |
| Stable acceptance contract    | Re-running product analysis cannot silently alter the active spec/capability revision. Newly discovered limitations create an explicit contract-change record and preserve the old candidate/evidence.                                                                                                               |
| Artifact-based evidence reuse | Equivalent validation on the same artifact/spec/environment is usable by delivery regardless of invoking role. A missing builder stamp triggers only a genuinely missing check, not a repeat planning cycle.                                                                                                         |
| Capability honesty            | A request requiring shared persistence cannot be marked fully implemented when the capability contract disallows every persistence route. An agreed demo is labeled and accepted as such from the beginning.                                                                                                         |

The successful-run requirement remains the whole requested application. Incremental checkpoints preserve work; they are not permission to declare a partially implemented request complete.

## 7. Limitations and retrospective questions that public research cannot answer

- Public research initially resolved CrewAI docs to v1.15.41 and inspected selected source at commit `9b38b5453c41feea94c3f88793fcf484d297bb0a`. After the parent supplied Formlane's 1.15.40 pin, the **1.15.40 production-architecture and checkpointing pages were also read** and support the same Flow-first recommendation and checkpoint caveats [C13, C14]. Other source-level details remain observations of the cited source revision, not a claim that every line is identical in the deployed wheel. DBOS current docs likewise require checking against the 3.5.0 pin before using version-specific APIs.
- Public CrewAI docs have stale language, such as a `max_retries` removal note saying v1.0.0 within v1.15.41 docs [C3]. Source and the deployed pin govern behavior; marketing prose is not a runtime contract.
- No source cited establishes v0's private orchestration, its role count, repair budget, or persistence engine. The separate v0 research should constrain claims to public evidence.
- Maintenance status is a dated observation. A recent source push does not establish production reliability; a tutorial's success screenshot does not establish distributional success rates.
- No comparative model or framework benchmark was run. Recommended budget values and success-rate targets require a representative evaluation set and an agreed baseline.
- Parent-supplied evidence establishes the artifact's eight/ten checks, accepted review, changed disclaimer requirement, and 96 checkpoints. The main retrospective must retain exact local citations and map `step_limit` to its owning counter; distinguish actor-specific evidence from check coverage; establish when the contract changed; and identify the recoverable candidate/checkpoint boundaries. This report does not re-query or independently verify those private facts.
