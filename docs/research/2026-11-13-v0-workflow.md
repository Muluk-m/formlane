# v0 workflow research for Formlane

Research date and access date: **2026-11-13**. Scope: public Vercel/v0 documentation, public API/SDK contracts, and first-party app-builder examples. No Formlane source inspection, generation, deployment, production mutation, build, lint, test, or formatter execution was performed. The recommendations below are design proposals for the parent architecture review, not patches.

## Findings that change the design discussion

1. **The public v0 workflow makes running software available for inspection, then iterates on the same workspace.** Simple applications can go straight to implementation; complex applications warrant planning, but official guidance explicitly recommends incremental development and working core functionality at each stage. This supports a first runnable checkpoint, not mandatory specialist consensus before any code exists. [S1–S3]
2. **Do not mix the v0 product's version UI, the old v1 API, and the current v2 API.** The current migration guide explicitly says “Versions are gone”: v2 has durable chats, current files, message history, and restore-by-message. Product documentation still describes user-facing versions. Formlane can retain useful version milestones without copying an obsolete vendor resource model. [S4, S5, S12]
3. **A first-party, independently implemented app-builder example offers especially relevant evidence.** Vercel's Forma sample uses a saved coding-agent session, persistent sandbox, Postgres jobs/messages, background execution, streamed progress, and a deterministic build/preview check. Its worker explicitly reserves **270 seconds for build and preview** before observing the coding turn. This is concrete evidence for reserving delivery capacity; it is not evidence of v0's private orchestration. [S19–S22]
4. **A conversation ending is not proof of a working artifact.** v2 exposes pending questions/integrations/permissions, terminal finish reasons, current files, and a preview endpoint that can still return `null`. These are different states. Formlane should track them separately and make artifact readiness an observed gate. [S6–S9, S12]
5. **The evidence does not support “v0 never loops” or “v0 uses one agent internally.”** The public FAQ acknowledges repeated failures and credit consumption. Private planning prompts, routing, delegation topology, repair budgets, and success rates are not disclosed in these sources. [S15]

The user-reported Formlane observation—neighbor-tool-library has zero versions and hits `step_limit`—is accepted as task context. **Parent investigation update, not independently inspected in this research:** generated apps currently run in an opaque iframe with network, backend access, and browser storage forbidden; the lending request therefore produces only page-memory behavior. The parent also reports that the same artifact passed eight checks, the manager regenerated its brief during review and added a required no-persistence disclaimer, and ten checks later passed without any version being created. This corrects the initial assumption that no validation had occurred: the actual distinction is between checks running and an artifact becoming an accepted, persisted version. **[INFERENCE]** The rewrite must address capability mismatch, stable acceptance criteria, and promotion/persistence boundaries in addition to budget allocation. Increasing the limit alone cannot establish those contracts.

## What the public examples actually show

### v0 SDK examples: one workspace, iterative messages, observed preview

The SDK README demonstrates `v0.chats.create`, checks `response.error`, then calls `v0.chats.getPreview` using the new chat ID. The basic synchronous script only creates a chat and logs its ID; it does **not** establish that the resulting app passes acceptance checks. The basic streaming script consumes the stream and its final result. [S14]

The React example loads persisted messages, seeds `V0Transport`, resumes an unfinished assistant message, prevents another submission while generating, and implements a server stop request followed by stopping the client stream. This distinguishes durable generation from its browser connection. [S14a]

The larger first-party `examples/v0-clone` adds files, restore, duplicate, deployment actions, task controls, and Design Mode. Its README says Design Mode acknowledges Apply only after a successful final completion; a cache-refresh failure after a confirmed save must not duplicate the generation. It also explicitly says there is **no user account/authentication system** and all reachable users share the deployer's workspace. Treat it as an integration example. [S14b]

### Forma: stronger evidence for the orchestration boundary

Vercel's official guide, published 2026-09-11 and updated 2026-11-02, describes a v0-style builder called Forma. It is a separate app, not v0's released source or a claim about v0 internals. [S19]

Documented flow:

1. Authenticate/authorize the request, atomically save the user message/job/active-job pointer, and return the job ID.
2. Worker claims a lease, prepares the persistent workspace, and creates or retrieves a coding-agent session.
3. Start and expose the managed preview; record streamed agent progress while editing that same workspace.
4. Independently run a production build and check preview readiness before marking the operation ready.
5. Follow-up prompts reuse the session/files. Save & pause and reopen are lifecycle jobs; reopening does not send a new coding prompt. [S19, S20]

The inspected worker source sets a 760,000 ms job deadline and computes its observation budget as remaining time minus 270,000 ms, explicitly commenting “Reserve build + preview time.” It separates `editing` from `checking`, then runs `checkBuild` and `startPreview`. On a build error it records the error and finishes the job in an error state; it does not endlessly delegate a fix. [S21, `runJob` and `observeTurn`]

The agent creation script instructs a coding agent to use the existing workspace, preserve the managed dev server/port/config/scripts, avoid credential-requiring services for this sample, validate the build, repair errors, and summarize. This is one configured coding agent in this example, not proof that its provider cannot use subagents. [S22]

The sample also starts a starter preview before the requested changes finish. **[INFERENCE]** This is useful for transport/runtime readiness, but Formlane must not count a generic starter screen as the requested app's first useful version. The gate must include a request-relevant interaction.

## Capability discovery and three distinct outcomes

**Documented v0 evidence:** the full-stack guide describes real backend routes and database connections; integration handling explicitly discovers missing resources, pauses, connects them, and then resumes. The sandbox can execute server code and reach real services. Conversely, generation-time MCP access does not itself become a generated application's runtime API. [S3, S9, S11, S17] This is a materially different capability envelope from the parent-reported current Formlane runtime.

**[INFERENCE / PROPOSAL] Discover capabilities before promising behavior.** Match each requested journey to a runtime capability record: server execution, network destinations, durable application storage, authentication, secrets, uploads, external APIs, and publication targets. Distinguish `supported and configured`, `supported but setup required`, and `unsupported by this runtime`. A missing database credential is a setup blocker; a runtime that forbids every storage/network path is a platform capability gap. An agent cannot repair that gap by regenerating UI code.

| Outcome                   | Required evidence                                                                                                                                                                                                                        | What it does not mean                                                                                                              |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **Draft / first preview** | Saved generated source, identified revision, reachable isolated preview, and explicit capability/coverage status. A page-memory interaction may be useful for design review when labeled accordingly.                                    | It is not an accepted lending system, a completed request, or a published deployment. A generic starter is only runtime readiness. |
| **Accepted version**      | An immutable artifact is promoted against a stable acceptance contract; required interaction and persistence/security checks pass; evidence is bound to the exact artifact and contract revision; the version record is durably written. | A test count, final assistant text, or disclaimer does not substitute for requested product behavior.                              |
| **Published release**     | A chosen accepted version is deliberately released to its target environment, with deployment outcome and required environment configuration recorded.                                                                                   | Preview availability and acceptance do not authorize or prove publication.                                                         |

Do not withhold an inspectable draft because acceptance is blocked. Equally, do not promote a page-memory demo to an accepted full lending application. If the user explicitly chooses a session-only demo, that becomes a separate, clearly agreed acceptance contract; the agent must not silently impose that reduction. If the user expects real borrowing history and multi-user inventory, the current reported runtime yields **unsupported / platform capability required**, while the draft remains available for inspection. Building the missing runtime capability is a separate authorized engineering decision, not something this research executes.

Separate three forms of persistence:

- **Platform project persistence:** prompts, jobs, files, artifact history, version records, and saved preview configuration survive reconnects.
- **Runtime workspace persistence:** sandbox files/dependencies survive compute stop/restart; running processes must restart.
- **Generated-application data persistence:** loan records, inventory changes, users, and authorization state survive reloads and support the promised sharing semantics.

Only the third delivers durable lending behavior. Neither PostgreSQL behind Formlane nor durable DBOS replay supplies it automatically. Likewise, v0's persistent chat filesystem alone is not its database integration. [S3, S5, S11, S19, S23]

**[INFERENCE / PROPOSAL] Freeze the acceptance contract for each candidate.** Review findings should identify a failed criterion or propose an explicit contract amendment. Regenerating a brief must not silently add or remove criteria mid-review. A no-persistence disclosure may improve truthfulness, but it cannot turn a failed persistence requirement into a pass. An amendment gets its own contract revision and requires the appropriate product decision; previously observed results retain their artifact/contract identities. Once an artifact passes the current contract, deterministic promotion should persist the accepted-version record without another open-ended manager deliberation. Publication remains a later operation.

## Recommended workflow for Formlane

Everything in this section is **[INFERENCE / PROPOSAL]**, informed by sources above. It is not a reconstruction of private v0 code.

### Adopt

**1. Make an artifact checkpoint unavoidable.** Use an explicit controller-owned sequence: intake → resolve indispensable blocker if any → materialize a coherent candidate → run compiler/runtime checks → bounded repair if needed → persist an inspectable preview checkpoint → continue requested scope and review. A planner or specialist can contribute, but cannot redefine these controller transitions or consume the capacity reserved for validation and checkpointing.

**2. Define “first runnable” precisely.** It means persisted source for a meaningful slice of the user's request, a running preview tied to that exact artifact, and evidence that a representative interaction works. For neighbor-tool-library, a candidate example is browse actual seeded tool records, search/select a tool, and perform the agreed first action. If borrowing persistence is part of the first agreed slice, it must survive reload using the real configured storage. A placeholder page or falsely successful borrow button does not qualify. Later required features remain visible and must be completed before claiming the overall request is done.

**3. Use one accountable writer before the first useful checkpoint.** Give the builder the request, execution constraints, baseline files, available integrations, and acceptance journey. Specialists should return bounded decisions or diagnostics that the builder can consume; avoid a mandatory chain of specialist essays before materialization. A hard maximum handoff depth is a Formlane policy, not a discovered v0 setting. Default direct implementation for clear single-purpose requests; activate planning when unresolved product choices materially change implementation.

**4. Reserve validation and persistence resources outside agent discretion.** Keep separate allocations for generation, tool execution, validation, repair, and final checkpoint persistence. The exact budgets should be benchmarked; do not copy Forma's numeric timeouts to Python/CrewAI. The transferable rule is that the planner cannot spend the validator's allocation. If no candidate is produced within the generation allocation, preserve any partial workspace and return an explicit failure, not success or another unbounded delegation round.

**5. Make blocked input a durable state.** Distinguish missing user decision, missing credentials/resource, denied permission, unsupported platform, and implementation failure. Tie each blocker to a current run/revision and resume token. Continue independent implementation when possible. Do not ask about settled choices, auto-answer a real blocker, or repeatedly run the same tool without the missing prerequisite.

**6. Repair the exact candidate that failed.** Send the builder structured compiler/runtime/browser diagnostics, failing acceptance step, artifact identity, and remaining repair allowance. A repair must change the artifact or resolve the actual environmental issue before retrying. Preserve a previous working checkpoint while a new revision fails. Stop with the exact unresolved failure when the allowance is exhausted; do not declare the request delivered.

**7. Preserve one durable project/workspace identity across edits and reconnects.** Persist prompt/job identity, active phase, artifact revisions, diagnostics, and user-visible status. Treat browser reconnection, workflow replay, and provider transport recovery separately from starting another generation. DBOS can supply Formlane's durable execution boundary; this research does not imply replacing it with Vercel Queues.

**8. Separate readiness axes.** Track at least source saved, preview reachable, acceptance checked, integration connected, and publish/deployment status. A terminal assistant response, tool status, non-null preview URL, or successful HTML response is insufficient alone. In v2 the `bash.exitCode` schema is explicitly described as currently omitted; generic stream rendering cannot substitute for independent execution results. [S12]

**9. Treat integrations as actual external state.** Backend setup is mandatory whenever requested behavior requires it. Avoid hiding missing auth/storage behind fixtures or local state. Conversely, do not block an independent catalog UI on a payment integration that only a later requested step needs. Classify fixture data clearly; artifact restore must never imply an external data rollback.

### Reject

| Proposal to reject                                                        | Reason                                                                                                                    |
| ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Raise `step_limit` as the entire fix                                      | More opportunities to deliberate do not create an invariant that candidate generation/validation occurs.                  |
| Every specialist must sign off before any preview exists                  | No such prerequisite appears in the public v0 workflow; it delays the evidence specialists need.                          |
| Eliminate all planning and all clarification                              | Official guidance explicitly supports planning for complex apps and structured blocking questions.                        |
| Count a plan, generic starter, or final prose as version one              | None proves request-relevant working behavior.                                                                            |
| Remove Formlane versions because v0 API v2 removed versions               | API resource design is separate from user-visible checkpoints and reproducibility.                                        |
| Retry generation whenever SSE disconnects                                 | v0 documents reconnecting without a new generation; duplicates can waste resources or repeat side effects.                |
| Assume sandbox persistence means application database persistence         | Workspace lifecycle and business data lifecycle are different.                                                            |
| Copy the clone's shared-workspace authentication or public preview policy | The first-party sources explicitly disclose those sample limitations.                                                     |
| Copy v0's “production-like preview” language as proof of parity           | Cookie stripping, external permissions, production variables, and deployment configuration still require concrete checks. |
| Conclude v0 internals prove a single-agent architecture                   | Public APIs and independent samples cannot reveal private topology.                                                       |

## Testable journeys for a later implementation evaluation

These are proposed acceptance experiments, **not executed tests**. They should run against the same frozen product request and environment when the parent authorizes implementation evaluation.

| Journey                             | Setup and action                                                                                               | Observable pass criteria                                                                                                                                                                                                           |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Clear neighbor-tool-library request | Submit a complete, bounded brief with catalog, filtering, detail view, and a specified first borrowing action. | A non-placeholder saved revision and reachable preview appear; the named action works; validation is reached before the run's limit; remaining requested scope is explicit.                                                        |
| Broad complete request              | Include accounts, inventory, borrowing/returns, and admin management.                                          | First useful checkpoint arrives before polish; no silent scope removal; overall completion is withheld until every requested journey works.                                                                                        |
| Genuine ambiguity                   | Leave one consequential rule unresolved, such as whether borrowing requires owner approval.                    | One concrete blocked decision is shown and persisted; settled preferences are not reasked; answer resumes the same work.                                                                                                           |
| Missing database credentials        | Require server persistence but provide no configured database.                                                 | UI work can proceed where independent; setup is visibly blocked; no successful persisted-borrow claim; resume after real connection uses the same workspace.                                                                       |
| Unsupported storage/runtime         | Require durable multi-user lending while the configured runtime forbids network, backend, and browser storage. | Capability mismatch is identified before promising completion; an honest draft may be shown; no accepted lending version is claimed; the user is offered supported scope or a platform-capability change without silent reduction. |
| Mid-review brief drift              | Candidate passes a fixed contract; reviewer proposes a new disclosure or behavioral requirement.               | Existing evidence remains linked to its original contract; amendment is explicit; a disclaimer does not replace behavior; no endless review loop or lost promotion.                                                                |
| Passed checks without version       | All required checks pass for one artifact and stable contract.                                                 | The accepted version is durably persisted exactly once; reconnect/replay recovers it; a failed persistence step is visible and does not trigger code regeneration.                                                                 |
| Acceptance without publication      | Produce an accepted artifact but do not request release.                                                       | Draft and accepted-version states are visible; no production deployment occurs; later publication names the accepted artifact explicitly.                                                                                          |
| Compile failure                     | Introduce a broken import into the candidate.                                                                  | Validation captures the actual error; bounded repair changes the artifact; no recursive specialist loop; checkpoint readiness is withheld until repaired.                                                                          |
| Runtime/business failure            | App compiles but borrow action crashes or permits unavailable inventory.                                       | Representative interaction catches the defect; compiler success is not promoted to acceptance success.                                                                                                                             |
| Duplicate submit / browser refresh  | Disconnect during generation and reconnect; repeat the same submission identity.                               | One durable job/generation is associated with the request; history reconstructs without duplicates; no new paid generation merely to recover the UI.                                                                               |
| Edit after first checkpoint         | Change card layout and add a field after a successful borrowing flow.                                          | Revision provenance identifies its base; requested change works; previous flow still passes; prior working revision remains recoverable.                                                                                           |
| Restore                             | Restore an earlier code checkpoint after a bad edit.                                                           | Code/preview returns to the selected state; audit trail is preserved; external database rollback is neither assumed nor silently attempted.                                                                                        |
| Exhausted repair allowance          | Use a persistent reproducible failure.                                                                         | Run terminates with diagnostics and retained artifacts/last good preview; no fabricated success; no automatic full restart with an unbounded fresh budget.                                                                         |
| Pause/reopen                        | Stop runtime after saving, then reopen.                                                                        | Workspace/code restores; required processes restart; opening the preview does not send a new coding prompt or recreate an empty project.                                                                                           |
| Preview isolation/auth              | Exercise generated scripts, root-relative assets, authentication, and attempts to access another project.      | Host secrets/session are unavailable; ownership is enforced; legitimate preview app auth works under the actual proxy policy.                                                                                                      |

Measure time to first materialized candidate, time to first useful preview, pre-checkpoint handoffs, percentage reaching validation, repair count, end-to-end acceptance rate, and duplicate submissions. These are evaluation measures for the redesign, not a request to add unrelated production telemetry. Compare a direct builder with bounded specialist support against the present workflow using identical acceptance criteria; do not optimize solely for fewer tokens.

## Uncertainties and source conflicts

- **Private unknowns:** v0's actual internal agent graph, prompt templates, whether/how it delegates, its evaluation suite, model-specific failure rate, and internal step/retry budgets are not public evidence here.
- **No performance measurement:** No generations were run, so there is no empirical v0 latency, cost, reliability, or neighbor-tool-library outcome in this report.
- **Version naming:** Product docs describe versions; v2 migration removes version resources; v2 restore-by-message remains. These are different interfaces, not proof that recoverable history disappeared.
- **API-generation drift:** Search surfaced old `v0-sdk`/v1 routes alongside current `v0`/v2 docs. Current v2 base URL is documented as `https://api.v0.dev/v2`, with `https://v0.app/api/v2` permanently supported. Old v1 chats are not v2-compatible; migration transfers files via ZIP. [S5]
- **SDK sample inconsistencies:** The integration guide's first snippet accesses `message.parts` directly after `messages.send`, while the current SDK overview/examples use `{ data, error }` results. Treat conceptual pause/install/resolve semantics as evidence, but pin package/OpenAPI versions before copying code. [S9, S14]
- **Documentation quality:** The agentic-features page omits the numeric free-fix allowance. The general sandbox persistence guide contains a malformed code fragment (`'vercel/sandbox/node:24' correct?`). Neither is copied as executable code or a verified entitlement. [S10, S23]
- **Product claims versus guarantees:** The FAQ's “exactly as production” wording is broader than the documented preview proxy's cookie limitations. Real auth/integration journeys still need evaluation. [S13, S15]
- **Sample limits:** Forma's guide labels Agents API access as preview while the current repository says public beta, and the sample requires that specific API rather than merely Agents SDK/Responses access. This report does not infer that Formlane has that access or recommend a provider migration. [S19, S20]
- **Storage guarantees:** v0 describes filesystem persistence, but the inspected sources do not establish a complete backup SLA, disaster-recovery guarantee, or application database durability policy. General Sandbox snapshots are also not an application database. [S11, S23]
